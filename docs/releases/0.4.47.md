## Changes since 0.4.46

Production 2026-11-24 to 27: the 8 gateways (`web-node-*-01`) and the 8 hosts behind them (`web-redis-*`) refused every remote update. Their systemd units implied no_new_privs (the units written by `askio-monitor install` before 2026-11-24 set `PrivateDevices=`, `RestrictSUIDSGID=` and `LockPersonality=`, which make systemd set it for a non-root `User=`), and the root-owned `askio-monitor-updater` did not exist yet when they were installed (2026-11-18). An agent in that state has no privilege path at all, by design: someone with a root shell must run the installer's `upgrade` once. Askio learnt this only from each failed update command.

- **The heartbeat reports the update path.** Host agents and gateways send `self_update` in every heartbeat: the path an update would use (`root`, `updater`, `helper`, `sudo` or `none`), whether it is available, a reason code and text when it is not, and the no_new_privs, updater and helper facts behind it. It is re-checked every 5 minutes with the other capability checks (it reads `/proc/self/status`, checks files, runs `systemctl is-active` on the updater's path unit and, on hosts, `sudo -n -l install` / `sudo -n -l systemctl`; it changes nothing). Migration-enabled agents do not send it: they are updated by re-enrollment. The new `internal/selfupdate` package holds the decision; the gateway's `update_agent` handler uses the same one, so the reported path is the path an update takes.
- **An inactive updater is not used.** If `askio-monitor-updater.path` is installed but `systemctl is-active` says it is inactive or failed (exit 3), the gateway no longer stages the binary and writes a request nobody applies (which reported success and never updated). It falls back to the helper, or fails with "installed but not active" and the command to enable it. Any other `systemctl` failure (for example no D-Bus access from the sandbox) keeps the earlier behaviour and uses the updater.
- The monitoring heartbeat interval and every other loop are unchanged.

## Rollout notes

- Backend: ccycv/askio (agent fleet health, migration `20261128150000_agent_update_rollouts`) stores the report as `capabilities.self_update`, shows it in the version-drift panel and refuses an update the agent says cannot work. Older backends ignore the new heartbeat field.
- The backend's update script gets the same inactive-updater check in that PR, so hosts follow the same rule as gateways.
- Gateway-site agents that are still on a unit with no_new_privs and no updater keep refusing remote updates until `curl -sSL https://api.askio.cloud/agent-install.sh | sudo bash -s -- upgrade` runs once on each (gateways first). From this release on, the panel shows exactly which ones.
- Rollback target: `0.4.46` (above).
