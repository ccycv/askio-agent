## Changes since 0.4.43

- **The idle vulnerability inventory poll follows the backend.** When no capture is due, the agent asks again at the backend's `nextPollAt`, which the backend sets from `VULNERABILITY_INVENTORY_POLL_SECONDS` (60 s to 6 h). Before, the agent capped every wait at one minute, so each enrolled host polled once a minute whatever the backend said.
- A missing, unparseable or out-of-range `nextPollAt` (sooner than 15 s or later than 6 h) still falls back to one minute.
- **Unstable captures are admitted.** When the package state changes while the inventory is read, the agent downgrades verified origin receipts to `unknown` (`capture_state_changed`). It now also clears their installed evidence (`installedChecksumsSha256`, `installedFiles`); 0.4.43 kept it, and the backend refused every such completion with `INVENTORY_CAPTURE_MISMATCH` (67 of 100 `v2-instance-*` hosts on 2026-11-26). The backend from ccycv/askio (inventory admission PR) accepts both forms.
- **The heartbeat reports the inventory status.** A new `inventory_status` field carries the gate, whether the loop runs, and what the last inventory cycle did: outcome, failing stage (`claim`, `collect`, `prepare`, `upload_page`, `complete`), a reason code, package count, collection/provenance status and error codes, and capture/verification durations. Codes, counts and durations only. The backend stores it from ccycv/askio#124; an older backend ignores the field.
- The monitoring heartbeat interval, config poll and every other loop are unchanged.

## Rollout notes

- Requires the Askio backend that sets `nextPollAt` from `VULNERABILITY_INVENTORY_POLL_SECONDS` (ccycv/askio, inventory poll interval PR). An older backend sends the six-hour routine time, so a 0.4.44 agent would not pick up a requested refresh for up to six hours: deploy the backend first.
- With the backend default (60 s) nothing changes. A longer interval takes effect when the repository variable is raised and the backend released.
- Rollback target: `0.4.43` (above).
