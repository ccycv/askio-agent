## Changes since 0.4.39

Agent PRs #4 and #5, `50b8bbd..b80c24d`:

- **Passive vulnerability inventory collector**, off by default (`25bc9f8`), and **cached package provenance observations** (`d21e12e`). Both are documented in [PASSIVE_INVENTORY.md](../PASSIVE_INVENTORY.md) and [PASSIVE_PROVENANCE.md](../PASSIVE_PROVENANCE.md).
- **Versioned, reproducible release build.**
  - Added: `VERSION`, `make release`, the provenance manifest, `verify-release.sh`, the reproducibility check and CI.
  - `--version` keeps the `askio-monitor version X` prefix and adds build details on the same line.
- **Hard host opt-in gate for inventory**, with a 24-case gating test. See [ENROLLMENT.md](../ENROLLMENT.md).
- **What did not change:** no file under `internal/migration`, `internal/operations`, `internal/remediation`, `internal/discovery`, `internal/checks`, `internal/gateway`, `internal/audit` or `internal/store`, and neither `go.mod` nor `go.sum`.

## Behaviour with the backend's inventory flag off

The lab parity run on 2026-11-22 used linux/arm64 builds of `50b8bbd` (ADR-010 recipe) and `b80c24d` (release recipe), because there is no amd64 emulation locally. Each ran `start` for 100 s against a throwaway HTTPS backend. That backend answered the inventory routes with `404` (flag off) or `403` (not enrolled), the way Askio's routes do.

| Run | config | heartbeat | discovered-services | inventory-claim | Payload keys | Log lines |
| --- | --- | --- | --- | --- | --- | --- |
| 0.4.39, no `inventory` key | 2 | 4 | 2 | 0 | baseline | baseline |
| 0.4.40, no `inventory` key | 2 | 4 | 2 | **0** | identical | identical |
| 0.4.39, `inventory: {enabled: true}` | 2 | 4 | 2 | 0 | identical (key ignored) | identical |
| 0.4.40, `inventory: {enabled: false}` | 2 | 4 | 2 | **0** | identical | identical |
| 0.4.40, `enabled: true`, flag off (404) | 2 | 4 | 2 | 2 (t=3.7 s, 63.7 s) | identical | + 2 × WARN `passive inventory cycle incomplete` |
| 0.4.40, `enabled: true`, not enrolled (403) | 2 | 4 | 2 | 2 (t=3.8 s, 63.8 s) | identical | + 2 × WARN `passive inventory cycle incomplete` |

The only differences between 0.4.39 and 0.4.40 without opt-in are the version strings: heartbeat `agent_version`, the `User-Agent` and the `--version` line. An opted-in 0.4.40 host whose backend gate is closed sends one capabilities-only claim about every minute and logs one WARN for each. It collects nothing and uploads nothing.

2. Then, and only on the owner's instruction:

   git tag -a v0.4.40 b80c24d58d7506af40b67c3f55ad65293740c23f -m "askio-monitor 0.4.40 (sha256 6c3a8b9257976fd89d738f32b773443fc85f38e2a521e96955ffc313883b49b6)"

3. The tag points at the artifact's source commit, `b80c24d`, **not** at the commit that merges these notes. A build of the tag reproduces the same bytes: the tag is recorded only in the manifest, never in the binary.
4. Later commits on `main` that still say `VERSION 0.4.40`, such as the merge of these notes, are not the 0.4.40 release. The next source change must bump `VERSION` to `0.4.41`.

## Rollback

Restore the previous Askio release metadata and binary, which is `0.4.39`.

- **Hosts keep 0.4.40 until each is updated.** A host already on 0.4.40 stays there until its owner runs the per-agent update. That update installs the pinned 0.4.39 binary; the update script does not refuse a downgrade.
- **A host opt-in becomes inert.** 0.4.39 ignores an `inventory` stanza in its local config (lab run 3).
- **Keep `0.4.40` in Askio's `compatible_agent_versions` during a rollback.** The deploy guard blocks a backend deploy while any active migration run is bound to an agent version missing from that list.
